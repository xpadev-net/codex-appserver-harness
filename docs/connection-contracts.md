## Immutable kernel artifacts

Trusted main imports may describe repository/external sources; a Task may only publish its own Task provenance. These are generic bytes and do not replace product Candidate/SHA gates.

Import commits a capacity reservation before writing. The controller fsyncs private object bytes and the directory, then commits the manifest and notification intent together. Staged and deleting objects remain charged against Wave/controller limits. The same import key and content resume the same ID after restart; changed inputs conflict. Concurrent replay serializes file writes, and committed objects are never overwritten. Recovery reports unresolved partial/missing staged imports separately from committed imports; it never substitutes empty content.

File import confines normalized relative paths to the stored workspace using `os.Root`, checks readability/regular files and actual byte bounds, and rejects escapes, special files and hard links. Object access rejects symlinks, non-private permissions and hard links. Every read rechecks actual size and digest. Tools receive IDs/manifests/excerpts rather than object paths. Main owns its Waves; Tasks can read their own outputs, declared inputs and artifacts in bound completed dependency results. Cross-Wave/stale scope or policy and undeclared sibling access fail. Plan adoption and run reservation also recheck declared artifact bytes.

Retention starts from the producer Task's terminal time, or the Wave's terminal time for main imports. Unfinished Tasks protect their declared inputs, dependency results/evidence, own outputs and the transitive input provenance. Missing terminal timestamps retain data conservatively. GC saves a deletion intent before removing bytes and only releases capacity after saving expiration; a crash between removal and expiration is recoverable. Unknown staged imports stay charged for reconciliation. ## Durable wake/run input binding

`PendingWakeNotifications` selects current, unpaused inputs for the receiving session; delivery-acknowledged inputs remain eligible. A current completed/canceled Wave observation may wake its owning parent to report the outcome within the remaining deadline/budget; ordinary message/Task inputs cannot reopen terminal Wave work. The same notification-aware check is repeated at run binding and unstarted-intent recovery. `ReserveWake` stores a stable operation key, exact notification set, targets, preallocated run ID and digest-bound input snapshot before any process/turn starts. The snapshot includes the authoritative message bodies and provenance for selected receive notifications, plus controller-built context. HTML escaping is disabled. Bodies whose quotes/control/separator characters expand significantly use `body_encoding: base64` with `encoded_body_chunks`; concatenate and decode these chunks to recover the original bytes, then verify `body_digest` (SHA-256). Normal text uses `body_encoding: utf-8` and `body`. Every encoded inline value remains within 16 KiB and a single valid maximum-size body fits the transport without truncation. It enforces the 64 KiB/inline limits atomically: an oversized batch remains pending for a smaller batch or immutable context references. A reused key cannot change its inputs. Other notifications arriving later remain pending.

Notifications and mailbox entries become bound to the reserved run without being marked processed. This does not add global scheduling or process ownership; those remain Task_4/5.

Logical Task-result application updates the input decision in the same transaction as the result. Accepted waiting/blocked/result output marks input applied; an invalid or superseded/terminal result archives its input without claiming processing. Physical completion, delivery ack and a reply alone do neither. A known stopped failed/interrupted attempt may release unfinished input for an explicit new retry key/run; unknown outcomes cannot. The Task attempt counter is still reserved once for each actual run. Common main decision application is connected by Task_6, not by generic physical completion.

`ReconcileUnstartedWake` can retire obsolete input only if no run binding exists and the session has no live/prepared process. Pause alone retains the original intent. On a shared main batch, obsolete Wave input becomes history while other current Wave input returns to pending; the old snapshot and disposition remain auditable. ### Wave operation budgets (Task_4, operation accounting slice)

Wave admission freezes trusted `WaveOperationLimits`: 100 validation job attempts, one additional infrastructure retry per logical runner job, two review requests per fixed candidate (resource identity and SHA), 1,800 seconds per model turn and 3,600 seconds per review wait by default. Explicit limits are validated and stored with Wave creation; source replay cannot replace them. Timers and trusted profile definitions are connected in Task_5/8. `WaveOperationBudget` reports the persisted counts and adopted limits.

Runner and Cloud review capacity admission charges the cumulative Wave ledger in the same transaction as dispatch and resource ownership. Exact operation replay does not charge again or authorize a resend. Failure rolls back counters and leases together. Counts survive release, plan/scope changes, restart and WorkItem subdivision. WorkItem adapters in Task_8 must also enforce their existing bounds, using the same logical operation identity; their totals are not added to the Wave ledger a second time.

A runner retry names its previous operation and requires its trusted terminal proof to classify an infrastructure failure after process stop. Retry lineage remains bound to the same Wave/target/session/workspace, and all branches share the original job's retry count. Unknown, timed out, unstopped or unclassified results cannot authorize a retry. Reservations remain counted even when an audited non-start releases capacity. Review admission requires the fixed candidate SHA; changing the operation ID or plan revision cannot reset the candidate's count. Only a new candidate has a new review allowance.

Read-only startup inspection refuses older Waves without adopted operation limits or runner/review dispatch histories without budget bindings, before changing DB bytes, permissions or journal mode. They require explicit offline reconciliation/migration. These storage ports do not claim actual runner/Cloud execution or K/P acceptance.

### Deadline holds and process observations (Task_4, final ports)
